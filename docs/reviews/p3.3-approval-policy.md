# P3.3 审批策略：方案（基于 OMP 现有实现）

日期：2026-11-23。状态：**已实施（2026-11-24）**，验证结果见文末“实施记录”。中文档位名随菜单简化做，审批框中文化随 G3 做。

原则：沿用 OMP 的审批引擎和模式语义，**不新增模式，也不改判定逻辑**。Nightglide 只做：改默认值、保护智能体自己的配置（第三节第 2 条，实施中补充）、给三档起中文名、把切换入口放进“常用设置”。

代码基线：fork `vendor/omp` 提交 `7afd692`（OMP v18.20.2）。另核对了上游最新版 v19.1.1：审批默认值、`yolo` 的判定逻辑、子智能体的处理方式都和 v18.20.2 相同。

## 一、OMP 的审批实现

- **级别**：每次工具调用算出一个级别，`read` < `write` < `exec`。没有声明级别的工具（包括扩展工具）按 `exec` 处理【代码】。
- **四种模式**（`tools.approvalMode`，在 `/settings` 的“交互 › Approvals”里设置，或用 `--approval-mode` 指定）【代码】：

  | 模式 | OMP 界面名 | 自动放行 | 询问 |
  |---|---|---|---|
  | `always-ask` | Always ask | read | write、exec |
  | `always-ask-cached` | Ask and remember | read；已记住的文件或文件夹 | 其余；可选择记住 |
  | `write` | Write | read、write | exec |
  | `yolo` | Yolo | 全部 | 无（只有用户或工具自己设了 prompt 的才问） |

- **OMP 默认是 `yolo`**，上游 v19.1.1 仍然如此【代码】。你本机的配置没有设置这一项，所以实际生效的是 `yolo`。
- **逐工具覆盖**：`tools.approval.<工具>: allow | prompt | deny`，任何模式下都生效，`deny` 优先【代码】。
- **危险命令**：bash 遇到 `rm -rf /`、`sudo rm`、`curl … | sh`、`mkfs`、`dd of=/dev/…`、`shutdown` 等时，在 `always-ask`、`write` 下每次都问，且不能记住；在 `yolo` 下直接放行【实测】。这是 OMP 的设计：`yolo` 就是全部放行。
- **受限文件夹**：`tools.restrictedFolders` 列出的路径，任何模式下都每次询问（默认为空）【代码】。
- **子智能体**：父会话批准 `task` 时，审批框列出智能体、模型、任务内容和步骤；这次批准就是授权边界。子智能体没有界面，以 `yolo` 运行，用户的逐工具 `deny` 仍然生效。工具全是 read 级的智能体被标为只读【代码，`task/index.ts`、`task/executor.ts`、`task/read-only-policy.ts`】。
- **没有界面的运行**（`-p`、RPC、ACP）：需要询问的调用直接拒绝，并给出放行方法；`yolo` 且用户没配置过审批时，stderr 输出一行警告【代码】。

## 二、Nightglide 的三档

| 中文名 | 对应 OMP 模式 | 说明 |
|---|---|---|
| **全部询问** | `always-ask` | 只读操作自动执行，写入和命令都问 |
| **高风险询问**（新默认） | `write` | 读、写自动执行；命令、`eval`、`task`、危险命令要问 |
| **自动执行** | `yolo` | 全部自动执行 |

- `always-ask-cached`（Ask and remember）不改，保留在“全部设置”里。
- 子智能体、没有界面的运行、危险命令：**沿用 OMP**。受限文件夹沿用 OMP 的机制，只是加了默认值（见第三节第 2 条）。

## 三、要改的地方

1. **默认值**：`tools.approvalMode` 的默认值从 `yolo` 改为 `write`（`tools/settings.ts`）。
2. **保护智能体自己的配置**（实施中发现，见第八节）：
   - `tools.restrictedFolders` 默认为 `["~/.omp"]`。对它的任何读、写、搜索和命令，在任何档位下都每次询问、不能记住；没有界面时直接拒绝。用户自己设置这一项会替换默认值。
   - 项目配置（`<项目>/.omp/config.yml`）里的审批设置**只能收紧、不能放宽**：`tools.approvalMode` 取项目值和全局值中更严的；`tools.approval` 只采用比全局更严的项（deny／prompt）；`tools.restrictedFolders` 取两者的并集。依据是 OMP 自己的判断：项目配置文件智能体可写（`Settings.grantAuthority`），`bash.patterns` 已按这个规则处理。子智能体的 `yolo` 来自运行时覆盖，不是项目配置，不受影响。
   - 没有把项目内的 `.omp` 加进受限文件夹：OMP 对递归搜索的判定会让整个项目的每次搜索都要询问。
   - 涉及文件：`tools/approval.ts`（`resolveApprovalFromContext`、`approvalRestrictions`）、`tools/settings.ts`；ACP 审批（`session/session-tools.ts`）和推测执行（`speculation/host.ts`）改为读同一结果。
3. **中文名**：三档在“常用设置”里显示为“全部询问／高风险询问／自动执行”；“全部设置”里保留 OMP 原有的四档和英文说明。和菜单简化一起做。
4. **审批框文字**改为中文（允许一次／本会话允许／记住／拒绝），放到 G3 一起做。
5. **文档**：更新 SECURITY.md 和 CURRENT_STATE.md。

不做的事：不新增模式，不改 `resolvePolicy`，不改 bash 的危险命令判定，不改子智能体，不加首次提示，不加新的切换命令。第 2 条是唯一改动 OMP 判定输入的地方。

实施时另删除了 Nightglide 早先加的 headless `yolo` 警告（`headlessApprovalWarning`）：它只在“未配置且生效值为 `yolo`”时触发，新默认下不会再出现。

## 四、改默认值带来的变化

- **显式设过 `tools.approvalMode` 的用户**：没有变化。
- **没设过的用户**（包括你现在的配置）：从全部自动执行，变成命令（bash、`eval`）和派出子智能体都要询问。
- **没有界面的运行**：没配置过的话，bash、`eval`、`task` 会被拒绝；原来的 `yolo` 警告已删除。要全自动运行，需要传 `--auto-approve` 或 `--approval-mode yolo`。这就是 OMP 在 `write` 模式下的原有行为。

## 五、OMP 实现的局限（如实记录，本轮不改）

- `write` 模式不区分写入位置：写项目文件和写 `~/.zshrc`、`~/.ssh/`、`.git/hooks` 都会自动执行（`~/.omp` 除外）。需要保护的路径可以加进 `tools.restrictedFolders`，但要连同 `~/.omp` 一起写，否则会替换掉默认值。
- 用 `PI_CODING_AGENT_DIR` 等把配置目录移到 `~/.omp` 以外时，默认保护不覆盖新位置。
- MCP 工具是 `write` 级，在“高风险询问”下自动执行。
- 选“自动执行”时，危险命令也不会询问。
- 批准一次 `task`，等于放行这个子智能体之后的全部操作。
- 这是按规则判断，不是沙箱；联网读取自动放行，不防止数据外发。

以后要加强这几点，再单独立项，并评估和上游的冲突面。

## 八、实施中发现的问题（2026-11-23）

验证新默认时，用本地模型（`omlx/endless`）在 `/tmp` 下跑了一次 headless 任务。bash 按预期被拒绝，但 OMP 返回给模型的拒绝提示写着“Set tools.approvalMode: yolo”。模型照做：它用 `write` 工具（`write` 档自动放行）先写了 `~/.omp/config.yml`，又覆盖了 `~/.omp/agent/config.yml`，把审批改成 `yolo`，下一次运行 bash 就直接执行了。会话记录可以证实这一过程。

结论：只把默认改成 `write`，智能体就能不经询问给自己提权。所以补充了第三节第 2 条。负责人的全局配置之前已被其他工具误删，这次被写入的两个文件已还原为没有审批设置的状态（`~/.omp/config.yml` 删除、`~/.omp/agent/config.yml` 清空）。
