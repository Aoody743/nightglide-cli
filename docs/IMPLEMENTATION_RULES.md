# 工程执行规范

适用于后续开发者和 AI。以 [产品方向](PRODUCT_DIRECTION.md)、[开发计划](DEVELOPMENT_PLAN.md) 和 [现状](CURRENT_STATE.md) 为依据；更具体的任务可以收窄范围，但不能暗中改变已确认的产品方向。

## 每次任务的执行方式

1. 阅读相关代码、当前工作树状态、对应计划与已有测试；确认实际入口和上游行为。保留用户及其他开发者的未提交改动。
2. 一次只实现一个可验证的任务切片。写清目标、涉及入口、数据来源、影响范围及验收方式；功能依赖未解决时先处理依赖，不用模拟数据冒充真实能力。
3. 沿用 OMP 已有组件、配置、事件和测试方式，尽量局部修改。跨包或 fork 内核改动须说明原因，并考虑上游升级与兼容性；不为未来可能的需求提前搭建复杂框架。
4. 覆盖成功、失败、取消和必要的边界；涉及输入、权限、模型派发或配置保存时，测试真实行为和错误路径。敏感信息不得出现在测试输出。
5. 汇报实际完成内容、涉及的入口、运行过的验证、失败及未验证内容；不以生成的截图、测试数量或文档勾选代替实际验证。任何历史测试结果必须标明提交、时间和环境。

## 保持 OMP 能力

- 不得为了界面改造直接移除或绕开会话、输入、工具、审批、扩展、MCP、LSP、计划模式、子智能体、键盘操作、命令行和已有配置等能力。
- 新界面需要说明事件来源与 OMP 的映射，不能用展示层临时状态声称操作已成功。工具或任务状态必须来自真实事件；不可得的信息显示未知或不显示。
- 若视觉效果与 scrollback、焦点、输入或上游控制协议冲突，先做小型原型并报告取舍，再决定架构；不得通过截断历史、禁用能力或更换入口来隐藏冲突。
- 修改 `vendor/omp` 需分别记录 fork 的提交与主仓子模块指针；按项目发布流程确认 fork 可访问和更改可追溯。不要把两个仓库混成一份无版本的变更。

## 真实验证与记录

| 证据类型 | 能证明什么 | 不能单独证明什么 |
|---|---|---|
| 源码审查 | 存在某条实现和代码路径 | 运行成功、外部服务可用或视觉合格 |
| 单元/组件测试 | 指定输入下断言成立 | 真实模型、用户终端与完整交互 |
| 终端/集成测试 | 所测入口、终端和环境中的实际行为 | 所有终端、平台和模型均可用 |
| 实际服务与人工画面验证 | 指定配置下的实际体验 | 其他服务、设备和终端的结果 |

每项记录提供日期、主仓及 fork 版本、操作系统/终端/尺寸、命令或操作、结果及局限；跳过或受阻不标为通过。凭据和私人会话不得进入证据。视觉截图必须来自实际应用，录屏验证持续动效和输入不中断；附静态和无动效模式。

## 动效与兼容性

- 场景占位固定，按可用空间渐进展示；80×24 下输入、正文及审批优先。视口变化不得导致内容丢失、焦点错乱或无限重绘。
- 审视现有渲染方式和终端 scrollback，先测量小型真实原型。支持无动效；检查定时器/订阅在完成、切换、退出、异常、取消和 resize 下的清理。
- 不能只测试一个理想的 ASCII 示例：覆盖 CJK、宽字符、长路径、颜色和非彩色/有限色回退。对比度检查需明确前景与实际背景；不以计算结果单独宣称全部终端无障碍。
- 兼顾动画和输入响应，在真实环境测试；指标取自基线和实测，不编造 FPS 或 CPU 数字。

## 安全与配置

- 默认审批目标为高风险询问，但需先审查 OMP 实际工具审批及配置优先级。未知命令、工具、权限继承、headless 模式和已有用户配置须有明确、可测试的策略；未经验证不能称为安全沙箱。
- 复用现有配置和凭据方式前检查覆盖、存储及迁移语义；配置取消或失败不能泄漏密钥或破坏原设置。云端调度遵循设置向导中用户作出的选择，不增加未经讨论的首次调用弹窗。
- LOCAL、权限和隐私承诺只覆盖真正经过验证的范围；模型端点在本机不代表其背后的服务不会转发。

## 文档规则

当前事实写入 [CURRENT_STATE.md](CURRENT_STATE.md)，新增决定写入 [PRODUCT_DIRECTION.md](PRODUCT_DIRECTION.md)，任务状态与验收写入 [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md)。历史报告保留，不在其中追加互相矛盾的“全完成”声明。计划完成需链接到具体验证记录；提议、已实现和已验证分别标识。
